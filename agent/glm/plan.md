### Задача 1. Техническая ревизия внешних зависимостей

**Контекст проекта (кратко).** PIBOX — обёртка, запускающая терминальный AI-агент Pi Coding Agent в изолированном Docker-контейнере. Домашняя директория агента `/home/pi` монтируется с хоста (`PIBOX_DIR/env/<name>`), текущий каталог пользователя монтируется как `/home/pi/workspace`. Состояние агента, его конфиги и локально установленные тулчейны переживают перезапуск. Цель этой задачи — до начала кодирования проверить все внешние допущения, чтобы не обнаружить их посреди реализации.

**Цель.** Зафиксировать в `docs/NOTES.md` проверенные факты о Pi, Node.js, mise, пакетах Ubuntu и Docker.

**Что нужно сделать.**

1. **Pi Coding Agent.** Установить локально на тестовой машине (`npm install -g --ignore-scripts @earendil-works/pi-coding-agent`) и зафиксировать:
   - имя и путь CLI-бинарника (ожидается `pi`);
   - требуемую версию Node (проверить `engines` в `package.json` пакета; убедиться, что Node 18 из Ubuntu 24.04 достаточен, иначе зафиксировать минимальную версию и источник Node — см. задачу 3);
   - что установка с `--ignore-scripts` даёт рабочий `pi --version` (флаг отключает postinstall-скрипты — если что-то ломается, это надо знать заранее);
   - фактическую структуру `~/.pi/agent/` после первого запуска: какие подкаталоги создаются (`sessions/`, каталоги расширений/скиллов), где лежат настройки;
   - формат и расположение файла моделей: поддерживается ли `~/.pi/agent/models.json`, какая у него схема, как описывается кастомный провайдер с произвольным `baseUrl` (для `http://host.docker.internal:8080`);
   - какие переменные окружения Pi читает для API-ключей.

2. **Docker.** Зафиксировать: минимальную версию Docker, поддерживающую `--add-host host.docker.internal:host-gateway` (20.10+); поведение вложенных bind-mount (`-v env:/home/pi -v ws:/home/pi/workspace` — убедиться, что Docker корректно монтирует вложенный путь поверх внешнего).

3. **Пакеты Ubuntu 24.04.** Прогнать весь список пакетов из ТЗ через `apt-cache policy <pkg>` (в контейнере `ubuntu:24.04`) и выписать **реальные имена пакетов**. Важно: в списке из ТЗ есть имена утилит, которые не являются пакетами — `cat` и `find`, `xargs` входят в `coreutils`/`findutils` и уже есть в базовом образе. Если пакет не существует — исключить его из списка и пометить это в NOTES. Заодно проверить, что `gosu`, `tini`, `yq`, `xxd`, `hexedit` доступны (universe-репозиторий включён в docker-образе Ubuntu 24.04 по умолчанию — убедиться).

4. **mise.** Проверить: способ глобальной установки без записи в home (скачивание tarball с GitHub Releases в `/usr/local/bin/mise`), пути хранения данных по умолчанию (`~/.local/share/mise`, шимы в `~/.local/share/mise/shims`) — именно там окажутся тулчейны, установленные агентом, и они будут переживать перезапуск, т.к. home смонтирован с хоста.

**Критерии готовности.** `docs/NOTES.md` существует, содержит ответы по всем четырём пунктам, включая подтверждённый список apt-пакетов и пример валидного `models.json`. Все спорные места помечены `TODO/уточнить`.

**Подводные камни.** Не начинать Dockerfile до проверки версии Node — это самая вероятная точка переделки.

### Задача 2. Каркас репозитория

**Контекст проекта (кратко).** PIBOX — Docker-песочница для Pi Coding Agent: `/home/pi` внутри контейнера — это смонтированный с хоста каталог окружения, текущая директория пользователя становится `workspace` агента. Репозиторий содержит исходники, из которых `install.sh` разворачивает рабочую инсталляцию в `PIBOX_DIR` (по умолчанию `~/pibox`).

**Цель.** Создать структуру репозитория и общие соглашения, чтобы дальнейшие задачи заполняли заранее согласованные места.

**Что нужно сделать.**

1. Создать структуру:

```
pibox/
├── Dockerfile
├── .dockerignore
├── entrypoint.sh
├── run.sh              # исходник CLI; после установки живёт как PIBOX_DIR/bin/pibox
├── install.sh
├── models.json         # шаблон конфига моделей (копируется install.sh в PIBOX_DIR/env/)
├── env-template/       # заполняется в задаче 4
├── tests/
│   └── smoke.sh
├── docs/
│   └── NOTES.md        # из задачи 1
└── README.md
```

2. **`.gitattributes`**: принудительно LF для скриптов — критично, CRLF из-за `core.autocrlf` на Windows сломает `entrypoint.sh` внутри образа:
```
*.sh   text eol=lf
Dockerfile text eol=lf
```

3. **`.gitignore`**: `docs/NOTES.local.md`, временные файлы, `*.log`. ВАЖНО: `env-template/` коммитим (это шаблон), но никогда не коммитим реальные окружения, ключи, `models.json` с ключами — в шаблонном `models.json` на месте ключей только плейсхолдеры.

4. **Соглашения для всех shell-скриптов** (оформить в `docs/CONVENTIONS.md`):
   - `#!/usr/bin/env bash`, `set -euo pipefail`;
   - все сообщения об ошибках — с префиксом `pibox: error: ...` и советом, что делать;
   - скрипты должны проходить `shellcheck` (добавить его в CI или как pre-commit);
   - человекочитаемые логи шагов (`echo "==> ..."`), чтобы пользователь видел, что происходит при первом запуске.

5. Опционально: минимальный GitHub Actions workflow — `shellcheck` на PR + `docker build` для проверки собираемости.

**Критерии готовности.** `git init`, структура на месте, `shellcheck` и `git check-attr` (LF) проходят на пустых заглушках.

**Подводные камни.** Не размещать в репо исполняемые файлы без бита execution — при копировании через `install.sh` права выставляются `chmod` явно, но в git rights по умолчанию сохраняются; проверить `git update-index --chmod=+x` для скриптов.

### Задача 3. Dockerfile (multi-stage сборка)

**Контекст проекта (кратко).** Pibox-контейнер — это Ubuntu с предустановленным Pi-агентом и базовым набором инструментов. Всё тяжёлое (компиляторы, отладчики) агент ставит сам локально в `~/.local` через mise уже в-runtime, поэтому образ должен быть компактным. Ключевое ограничение: **всё в образе ставится глобально** (в `/usr`, `/usr/local`), потому что `/home/pi` при запуске полностью подменяется bind-mount'ом — всё, что установлено в home, потеряется.

**Цель.** Собрать образ `pibox:latest` на базе Ubuntu 24.04: базовый набор пакетов, Node.js + глобально установленный `pi`, глобальный mise, эталонный home в `/opt/skel`, пользователь `pi`, entrypoint.

**Детальная инструкция.**

1. **Общая схема multi-stage.** Использовать официальный node-образ как источник Node и как builder-стадию для npm:

```dockerfile
ARG NODE_IMAGE=node:22-slim
ARG PI_VERSION=latest

# ---- builder: ставим pi в staging-префикс, кэш npm остаётся здесь ----
FROM ${NODE_IMAGE} AS builder
ARG PI_VERSION
RUN npm config set prefix /staging \
 && npm install -g --ignore-scripts "@earendil-works/pi-coding-agent@${PI_VERSION}" \
 && npm cache clean --force

# ---- runtime ----
ARG UBUNTU_VERSION=24.04
FROM ubuntu:${UBUNTU_VERSION}
```

   В runtime скопировать **дважды** из builder: `/staging/` (сам пакет pi) и `/usr/local/` (node+npm из базового node-образа):
```dockerfile
COPY --from=builder /usr/local/ /usr/local/
COPY --from=builder /staging/ /usr/local/
```
   Так node не ставится через apt (версия в Ubuntu может не подходить — см. NOTES из задачи 1), а multi-stage несёт реальную пользу: npm-кэш и метаданные установки не попадают в финальный образ.

2. **apt-пакеты.** Один многострочный `RUN` с очисткой:
```dockerfile
RUN apt-get update \
 && DEBIAN_FRONTEND=noninteractive apt-get install -y --no-install-recommends \
      ca-certificates locales tzdata lsb-release gosu tini \
      less grep sed gawk diffutils file xxd procps psmisc tmux \
      curl wget openssl iproute2 iputils-ping openssh-client dnsutils lsof \
      git tar gzip unzip rsync zip bzip2 xz-utils zstd lz4 \
      python3 python3-pip python3-venv \
      jq ripgrep yq vim htop ncdu hexedit \
 && rm -rf /var/lib/apt/lists/*
```
   Список сверить с NOTES задачи 1: несуществующих пакетов быть не должно, фиктивные имена (`cat`, `find`, `xargs`) — исключить.

3. **Locale и время:**
```dockerfile
RUN locale-gen en_US.UTF-8 && update-locale LANG=en_US.UTF-8
ENV LANG=en_US.UTF-8
```

4. **mise — глобально.** Скачать бинарник напрямую в `/usr/local/bin` (не через `mise.run`-инсталлер — тот пишет в home):
```dockerfile
ARG MISE_VERSION=<актуальная из GitHub Releases>
RUN ARCH="$(dpkg --print-architecture)" \
 && curl -fsSL "https://github.com/jdx/mise/releases/download/${MISE_VERSION}/mise-linux-${ARCH}.tar.gz" \
    | tar -xz -C /usr/local/bin mise \
 && mise --version
```
   Не задавать `MISE_DATA_DIR` — mise по умолчанию хранит тулчейны в `~/.local/share/mise`, и это именно то, что нужно: они попадут в смонтированный env и сохранятся.

5. **Пользователь и эталонный home:**
```dockerfile
RUN useradd --create-home --uid 1000 --shell /bin/bash pi
```
   Затем сформировать в `/home/pi` дотфайлы, которые должны попасть в skel: минимум кастомный `.bashrc`/`.profile` (PATH с `~/.local/bin` и `~/.local/share/mise/shims`, `eval "$(mise activate bash)"`, удобный PS1) — но только если аналогичные файлы не решено держать целиком в `env-template` (согласовать с задачей 4; правило: env-template — источник правды для дотфайлов, `/opt/skel` — фолбэк). После этого:
```dockerfile
RUN cp -a /home/pi /opt/skel
```
   (Содержимое `/home/pi` в образе можно не удалять — bind-mount всё равно его скроет, но skel обязан существовать.)

6. **Финальные штрихи:**
```dockerfile
COPY --chmod=755 entrypoint.sh /entrypoint.sh
ENV HOME=/home/pi
WORKDIR /home/pi/workspace
ENTRYPOINT ["/entrypoint.sh"]
CMD ["pi"]
```
   `.dockerignore` в корне репо: исключить всё, кроме `Dockerfile` и `entrypoint.sh` (build-контекст будет маленьким и быстрым).

7. **Проверка сборки:**
```bash
docker build -t pibox:latest .
docker run --rm pibox:latest pi --version
docker run --rm pibox:latest bash -c 'which pi mise node; id pi; ls /opt/skel'
```
   Образ должен собираться без предупреждений о несуществующих пакетах; `pi`, `mise`, `node` должны быть в `PATH` глобально.

**Критерии готовности.** Образ собирается `docker build` за разумное время; все бинарники из п.7 доступны; размер образа проверить `docker images` и записать в NOTES (ориентир — заметно меньше образа «всё включено»).

**Подводные камни.**
- Не ставьте ничего через `npm i -g` от пользователя `pi` и не запускайте `mise` установкой тулчейнов при сборке — всё это попадёт в home и исчезнет.
- `--ignore-scripts`: если после установки `pi --version` падает (нативные postinstall-зависимости), зафиксировать проблему в NOTES и обсудить — возможно, для конкретного пакета понадобится исключение.
- Не пинать теги «latest» для Ubuntu — зафиксировать `24.04`; для node — явный мажор (22).

### Задача 4. Шаблон окружения `env-template/`

**Контекст проекта (кратко).** Каждое окружение PIBOX (`default`, `php8`, …) — это каталог на хосте, монтируемый как `/home/pi` в контейнер. Новое окружение создаётся копированием `env-template`. Внутри окружения живут: конфиги Pi, сессии, пользовательские расширения и скиллы, а также тулчейны, поставленные через mise. `env-template` — «заводское» содержимое home.

**Цель.** Наполнить `env-template/` минимальным, но полезным содержимым.

**Детальная инструкция.**

1. **Структура Pi.** По результатам задачи 1 создать каталоги, которые использует Pi (структуру сверить с фактической):
```
env-template/
├── .pi/agent/
│   ├── sessions/          # пусто, каталог создаётся заранее, чтобы не было проблем с правами
│   ├── extensions/        # README-заглушка: как класть кастомные расширения
│   └── skills/            # README-заглушка
├── .bashrc
├── .profile
├── .gitconfig
├── .gitignore_global      # опционально: общие игноры
└── .tmux.conf             # tmux есть в образе — дать рабочую конфигурацию по умолчанию
```
   В каждый «направляющий» каталог положить короткий `README.md` с описанием назначения — агент сможет читать их и понимать, куда что класть.

2. **ВАЖНО: не включать `models.json` в env-template.** По архитектуре модели конфигурируются отдельно: шаблон лежит в репо (`models.json` в корне), `install.sh` кладёт его в `PIBOX_DIR/env/models.json`, а `run.sh` копирует в конкретное окружение при его первом запуске. Иначе обновление конфига моделей не дошло бы до уже созданных окружений. Содержимое шаблонного `models.json` — из задачи 1 (кастомный провайдер, `baseUrl: http://host.docker.internal:8080`, без реальных ключей — только плейсхолдеры/ссылки на env-переменные).

3. **`.bashrc`** (интерактивные сессии внутри контейнера, tmux и т.п.):
   - `PATH="$HOME/.local/bin:$HOME/.local/share/mise/shims:$PATH"`;
   - `eval "$(mise activate bash)"` (с защитой `command -v mise`);
   - разумные `HISTSIZE`, `HISTTIMEFORMAT`, `PS1` с индикатором pibox (чтобы было видно, что мы внутри контейнера).

4. **`.gitconfig`** — безопасные дефолты: `init.defaultBranch = main`, `push.default = simple`, закомментированные плейсхолдеры `user.name`/`user.email`. Никаких `safe.directory` — это решается в entrypoint/CLI (задача 5/6).

5. **Права и чистота:** файлы должны быть `644`/каталоги `755`; в шаблоне не должно быть ничего секретного (он в git).

**Критерии готовности.** `cp -a env-template/. /tmp/fakehome/ && tree /tmp/fakehome` даёт ожидаемую структуру; `models.json` в шаблоне отсутствует; shellcheck-чисто (если есть sh-вставки).

**Подводные камни.** Не переусложняйте шаблон: его содержимое копируется в каждое новое окружение и затем живёт своей жизнью — всё «умное» (инициализация при запуске) должно быть в entrypoint, а не в данных шаблона.

### Задача 5. `entrypoint.sh`

**Контекст проекта (кратко).** Entrypoint выполняется в контейнере от root при каждом запуске, до старта агента. Его работа: подстроить пользователя `pi` под UID/GID хост-юзера (чтобы файлы в workspace принадлежали хосту, а не root), при первом запуске смержить эталонные дотфайлы из `/opt/skel` в смонтированный home и передать управление агенту `pi` от пользователя `pi` через `gosu` под `tini`.

**Цель.** Рабочий `/entrypoint.sh`, реализующий контракт с задачей 3: env-переменные `HOST_UID`, `HOST_GID` (по умолчанию 1000), маркер инициализации, `PIBOX_GIT_SAFE`, exec-цепочка `gosu pi:pi tini -- pi "$@"`.

**Детальная инструкция.**

1. **Каркас:** `#!/usr/bin/env bash`, `set -euo pipefail`, логирование каждого шага.

2. **Динамическая UID/GID.**
```bash
HOST_UID="${HOST_UID:-1000}"
HOST_GID="${HOST_GID:-1000}"
if [ "$HOST_UID" = "0" ] || [ "$HOST_GID" = "0" ]; then
    echo "pibox: refusing to run as root" >&2; exit 1
fi
CUR_UID="$(id -u pi)"; CUR_GID="$(id -g pi)"
if [ "$CUR_UID" != "$HOST_UID" ]; then
    usermod -o -u "$HOST_UID" pi
    # чиним владельца файлов, созданных контейнером под старым UID
    find /home/pi -xdev -user "$CUR_UID" -exec chown -h "$HOST_UID" {} + 2>/dev/null || true
fi
if [ "$CUR_GID" != "$HOST_GID" ]; then
    groupmod -o -g "$HOST_GID" pi
    find /home/pi -xdev -group "$CUR_GID" -exec chown -h ":$HOST_GID" {} + 2>/dev/null || true
fi
```
   Комментарий для исполнителя: файлы env-каталога приходят с хоста уже с правильным владельцем; `find -user/-group` фильтрует только файлы, созданные внутри контейнера (сессии, кэши). На больших env это проход по дереву — приемлемо; отметить в комментарии.

3. **Первичная инициализация (skel-merge).**
```bash
MARKER="/home/pi/.pibox_skel_initialized"
if [ ! -e "$MARKER" ]; then
    echo "==> first run: merging /opt/skel into /home/pi"
    chown "$HOST_UID:$HOST_GID" /home/pi
    cp -rn /opt/skel/. /home/pi/
    chown -R "$HOST_UID:$HOST_GID" /home/pi   # ок: env ещё «свежий» и маленький
    touch "$MARKER"
    chown "$HOST_UID:$HOST_GID" "$MARKER"
fi
```
   `cp -rn` (no-clobber) не затирает пользовательские файлы; `/.` в конце — обязательно, иначе dot-файлы не скопируются. Предусмотреть повторный merge по флагу: если `PIBOX_RESYNC_SKEL=1` (ставится CLI-опцией `--resync-skel`) — удалить маркер перед проверкой.

4. **git safe.directory (опция).** Если `PIBOX_GIT_SAFE=1` — включить без записи в файлы, через переменные git-конфигурации:
```bash
export GIT_CONFIG_COUNT=1
export GIT_CONFIG_KEY_0=safe.directory
export GIT_CONFIG_VALUE_0=/home/pi/workspace
```

5. **Окружение для exec.** Критично: `gosu` меняет UID, но **не** переписывает переменные окружения. Экспортировать явно:
```bash
export HOME=/home/pi USER=pi
export PATH="/home/pi/.local/bin:/home/pi/.local/share/mise/shims:$PATH"
```
   Без этого Pi попытается писать сессии в `/root/.pi`, а mise-тулчейны не будут найдены.

6. **Передача управления:**
```bash
exec gosu pi:pi tini -- "$@"
```
   `"$@"` позволяет override: `docker run ... pibox bash` даст отладочную оболочку; `CMD ["pi"]` из Dockerfile — дефолт.

**Критерии готовности.** Локальные тесты (через docker):
```bash
docker run --rm -e HOST_UID=$(id -u) -e HOST_GID=$(id -g) \
  -v /tmp/fake-env:/home/pi pibox:latest bash -c 'id; ls -la ~/.pi/agent; echo $HOME'
```
   — `id` показывает хостовый UID/GID, `HOME=/home/pi`, дотфайлы из skel появились, маркер создан; повторный запуск не меняет уже существующие файлы (проверить `mtime` пользовательского файла).

**Подводные камни.**
- Самая частая ошибка таких entrypoint'ов — забытый `export HOME`. Тестировать обязательно.
- `usermod`/`groupmod` с занятым UID: `-o` допускает неуникальность; образ минимальный, конфликтов с системными пользователями быть не должно — но проверить `id pi` после смены.
- Не выполнять `chown -R /home/pi` на **каждом** запуске — только при первичной инициализации (иначе медленно на больших env и портит mtimes).

### Задача 6. `run.sh` — единая точка входа (CLI `pibox`)

**Контекст проекта (кратко).** PIBOX запускает Pi-агента в контейнере: текущий каталог пользователя монтируется как `/home/pi/workspace`, каталог окружения `PIBOX_DIR/env/<name>` — как `/home/pi`. CLI управляет окружениями, гарантирует, что агент не сможет случайно повредить собственную инсталляцию PIBOX, и собирает `docker run` с нужными флагами безопасности. После установки скрипт живёт как `PIBOX_DIR/bin/pibox`.

**Цель.** Реализовать `run.sh` с подкомандами и полной логикой запуска.

**Детальная инструкция.**

1. **Определение путей.** Скрипт должен знать `PIBOX_DIR`. При установке `install.sh` (задача 7) записывает его в скрипт подстановкой (например, заменяет плейсхолдер `__PIBOX_DIR__` на реальный путь). Дефолт на случай запуска из исходников: `PIBOX_DIR="${PIBOX_DIR:-$HOME/pibox}"`. Build-контекст образа: `PIBOX_DIR/docker`, имя образа: `pibox:latest` (переопределяется `PIBOX_IMAGE`).

2. **Синтаксис CLI:**
```
pibox run [OPTIONS] [--] [PI_ARGS...]     # run — дефолт при вызове без подкоманды
pibox build [--no-cache]
pibox env list | create NAME | remove NAME
pibox shell [-e NAME]                     # bash в контейнере (отладка)
pibox update
pibox doctor                              # проверки: docker, образ, пути, версии
pibox --help | --version
```
Опции запуска: `-e/--env NAME` (дефолт `default`), `-p/--publish SPEC` (повторяемый), `-E/--pass-env VAR` (повторяемый), `--env-file FILE`, `--memory`, `--cpus`, `--pids-limit`, `--resync-skel`, `--git-safe`, `--dry-run`, `--name`. Всё после `--` передаётся `pi` как аргументы.

3. **Валидации перед запуском (каждая — понятная ошибка и `exit 1`):**
   - `docker` установлен и демон отвечает (`docker info`);
   - имя окружения матчит `^[A-Za-z0-9][A-Za-z0-9._-]*$` (защита от path traversal);
   - образ существует, иначе сообщение: «выполните `pibox build`».

4. **Проверка безопасности каталогов (ключевое требование).** Workspace (текущий каталог) не должен совпадать с `PIBOX_DIR`, быть его подкаталогом или родителем:
```bash
ws="$(realpath "$PWD")"
pb="$(realpath "$PIBOX_DIR")"
nested() { [ "$1" = "$2" ] || [[ "$1" == "$2"/* ]] || [[ "$2" == "$1"/* ]]; }
if nested "$ws" "$pb"; then
    echo "pibox: error: workspace ($ws) overlaps with PIBOX_DIR ($pb)" >&2
    exit 1
fi
```
   (сравнения с `/` на конце исключают ложные совпадения префиксов вроде `/home/pix` vs `/home/pi`).

5. **Автосоздание окружения.** Если `PIBOX_DIR/env/<name>` отсутствует:
```bash
mkdir -p "PIBOX_DIR/env"
cp -a "PIBOX_DIR/env-template/." "PIBOX_DIR/env/$name/"
echo "==> created new environment '$name' from template"
```
   Затем — копирование моделей (идемпотентно):
```bash
dest="$PIBOX_DIR/env/$name/.pi/agent/models.json"
if [ ! -f "$dest" ] && [ -f "$PIBOX_DIR/env/models.json" ]; then
    mkdir -p "$(dirname "$dest")"
    cp "$PIBOX_DIR/env/models.json" "$dest"
fi
```

6. **Сборка команды `docker run`:**
```bash
docker run --rm \
  $([ -t 0 ] && [ -t 1 ] && echo -it) \
  --name "pibox-${env}-${$}" \
  -e HOST_UID="$(id -u)" -e HOST_GID="$(id -g)" \
  $([ "$GIT_SAFE" = 1 ] && echo "-e PIBOX_GIT_SAFE=1") \
  $([ "$RESYNC" = 1 ] && echo "-e PIBOX_RESYNC_SKEL=1") \
  --add-host=host.docker.internal:host-gateway \
  --cap-add=SYS_PTRACE --cap-add=NET_RAW \
  --memory "${PIBOX_MEMORY:-4g}" --cpus "${PIBOX_CPUS:-2}" \
  --pids-limit "${PIBOX_PIDS_LIMIT:-512}" \
  --shm-size 512m \
  -v "$PIBOX_DIR/env/$name":/home/pi \
  -v "$ws":/home/pi/workspace \
  -w /home/pi/workspace \
  $(собранные -p / -E / --env-file) \
  "$PIBOX_IMAGE" pi "${pi_args[@]}"
```
   Требования:
   - `-it` — только при интерактивном терминале (проверка `[ -t 0 ]`/`[ -t 1 ]`), иначе только `-i`;
   - вложенные bind-mount (`/home/pi` + `/home/pi/workspace`) работают корректно — Docker сам упорядочивает по глубине (проверено в задаче 1);
   - API-ключи: пробрасывать явно через `-E VARNAME` / `--env-file` (список имён переменных для Pi взять из NOTES задачи 1); автоматически ничего не пробрасывать — только явность;
   - порты `-p`: значение «как есть» в docker (формат `host:cont`, `host:cont/udp` и т.д.), опция повторяемая;
   - дефолты лимитов переопределяются env-переменными `PIBOX_MEMORY` и т.д. и флагами;
   - `--dry-run` печатает итоговую команду вместо запуска (обязателен — им же пользуются тесты задачи 8);
   - предупреждение (не запрет), если контейнер с этим env уже запущен: `docker ps --filter name=pibox-` — по метке env (добавить `--label pibox.env=$name`), чтобы не ловить гонки двух pi на одних сессиях.

7. **Подкоманды:**
   - `build`: `docker build -t pibox:latest "$PIBOX_DIR/docker"` (+ `--no-cache`);
   - `env list`: `ls PIBOX_DIR/env` с пометкой дефолта; `env create NAME` — то же копирование, что и автосоздание; `env remove NAME` — с подтверждением и запретом удалять `default`, пока не передан `--force`;
   - `shell`: тот же `docker run`, но команда `bash` вместо `pi`;
   - `update`: см. задачу 7 (логика общая — переиспользовать);
   - `doctor`: проверить docker, версию, образ, `PIBOX_DIR`, шаблон, вывод diag-инфы.

8. Прогнать `shellcheck`, вручную протестировать `--dry-run` для всех комбинаций.

**Критерии готовности.** `pibox --help` человекочитаем; `pibox --dry-run` из пустого каталога печатает корректную команду с автосозданным env и models.json; запуск из `PIBOX_DIR` и его подкаталогов блокируется; `pibox env create test && pibox -e test` работает.

**Подводные камни.**
- Порядок монтирований и `-w /home/pi/workspace`: workspace должен существовать на хосте (он есть — это `$PWD`).
- Кавычки и массивы bash при сборке аргументов — только массивы (`args+=(...)`), никакой конкатенации строк.
- `--add-host=host.docker.internal:host-gateway` требует Docker ≥ 20.10 — в `doctor` проверять версию.

### Задача 7. `install.sh`

**Контекст проекта (кратко).** Установщик переносит исходники репозитория в рабочую инсталляцию `PIBOX_DIR` (по умолчанию `~/pibox`): CLI-скрипт, build-контекст образа, шаблон окружения, шаблонный `models.json` и создаёт первичное окружение `default`. Повторные запуски установщика должны быть безопасными (обновление без потери пользовательских окружений).

**Цель.** Идемпотентный установщик с опциями.

**Детальная инструкция.**

1. **Опции:** `--dir PATH` (иначе `PIBOX_DIR` env, иначе `~/pibox`), `--force` (перезаписывать), `--no-path` (не трогать PATH), `--src PATH` (каталог исходников; по умолчанию — каталог самого install.sh).

2. **Шаги установки** (по ТЗ, с уточнениями):
   1. `mkdir -p "$PIBOX_DIR"/{bin,env,docker}`;
   2. скопировать `run.sh` → `PIBOX_DIR/bin/pibox` (chmod 755), **с подстановкой** `__PIBOX_DIR__` → фактический путь (sed) — см. задачу 6;
   3. скопировать build-контекст: `Dockerfile`, `entrypoint.sh`, `.dockerignore` → `PIBOX_DIR/docker/` (chmod 755 на entrypoint.sh);
   4. скопировать `env-template` → `PIBOX_DIR/env-template` (обновлять при повторной установке — это шаблон, пользовательских данных в нём нет; перезапись допустима);
   5. `env/default`: `if [ ! -d env/default ]; then cp -a env-template/. env/default/; fi` — никогда не трогать, если существует;
   6. `models.json` → `PIBOX_DIR/env/models.json` — копировать только если отсутствует (пользователь мог настроить ключи); при `--force` — перезаписать с предупреждением;
   7. PATH: определить rc-файл текущего шелла (`~/.bashrc` / `~/.zshrc`; для fish — вывести ручную инструкцию), добавить
      ```bash
      # >>> pibox >>>
      export PATH="$PIBOX_DIR/bin:$PATH"
      # <<< pibox <<<
      ```
      только если строки ещё нет (guard по маркеру `>>> pibox >>>`).

3. **Финальный вывод:** путь установки, `pibox build` как следующий шаг, `pibox --help`. Отдельно напомнить: отредактировать `PIBOX_DIR/env/models.json` (ключи/адреса) перед первым запуском.

4. **Идемпотентность:** второй прогон `install.sh` не ломает `env/*`, `env/default`, существующий `models.json`; обновляет только `bin/`, `docker/`, `env-template/`. Протестировать это явно.

5. Не запускаться под `sudo` без нужды: если `id -u = 0` — предупреждение и требование `--force` (docker обычно доступен пользователю через группу docker; root-инсталляция создаст файлы, принадлежащие root).

**Критерии готовности.** На чистой машине: `git clone … && ./install.sh` → `pibox build` → `cd ~/any-project && pibox` — полный путь работает. Повторный `install.sh` проходит без破坏 существующего окружения.

**Подводные камни.** Подстановка пути в `pibox` через sed — следить за спецсимволами в пути (`/` в разделителе sed → использовать `|`); проверить работу с путями, содержащими пробелы.

### Задача 8. Тестирование

**Контекст проекта (кратко).** PIBOX — контейнерная обёртка Pi-агента с монтируемым home-окружением и workspace. Перед сдачей нужно автоматически проверить инфраструктурные гарантии: изоляцию каталогов, подстройку UID/GID, персистентность, сеть и capabilities. Поведение самого агента (диалог с моделью) — вне скоупа автотестов, проверяется вручную.

**Цель.** `tests/smoke.sh` (зеленый прогон) + ручной чеклист приёмки.

**Детальная инструкция.**

1. **`tests/smoke.sh`** — последовательность проверок с выводом `PASS/FAIL` и итоговым кодом. Использовать `pibox --dry-run` и прямые `docker run`:
   - образ собирается, `pi --version`, `mise --version` работают;
   - `pibox --dry-run -e newenv` из пустого tmp-каталога: env создался, `models.json` скопировался, команда содержит правильные монтирования, `--cap-add`, `--add-host`, лимиты;
   - автосоздание env повторно не перезаписывает существующий файл в env (положить маркер-файл, сравнить mtime);
   - **UID/GID**: `pibox shell` в tmp-workspace → `id -u` равен хостовому; создать файл → на хосте `stat` показывает владельца-хостюзера;
   - **skel-merge**: первый запуск создаёт маркер `.pibox_skel_initialized`; пользовательский файл с именем из skel не перезаписывается;
   - **изоляция**: запуск из `PIBOX_DIR` и из его подкаталога → ненулевой exit и понятное сообщение;
   - **сеть**: внутри контейнера `curl -sS http://host.docker.internal:8080` (допустима любая HTTP-ошибка/отказ — главное, что имя резолвится) и выход в интернет (`curl -sI https://example.com`);
   - **capabilities**: `strace -e trace=write true` — ок; `timeout 5 tcpdump -c 1 -i eth0` — ок от пользователя pi;
   - **лимиты**: `docker inspect` запущенного контейнера показывает заданные memory/cpus/pids-limit;
   - **порты**: запуск `pibox -p 18099:80` + внутри `python3 -m http.server 80` + curl с хоста.

2. **Ручной чеклист приёмки** (прогнать и приложить к PR):

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Первый `pibox` в новом проекте | env создан, skel-merge, агент стартует в workspace |
| 2 | Второй запуск того же env | сессии/конфиги на месте, merge не повторяется |
| 3 | `pibox -e php8` | создался `env/php8`, изолирован от `default` |
| 4 | Установка тулчейна агентом (`mise use -g golang` или по задаче) | бинарник доступен, сохраняется после рестарта контейнера |
| 5 | Смена cwd между запусками | workspace смонтирован верно, права хостовые |
| 6 | `pibox update` / повторный install | окружения целы |
| 7 | Убийство контейнера по Ctrl-C / `docker stop` | чистое завершение, артефактов-зомби нет |

**Критерии готовности.** `smoke.sh` проходит целиком; чеклист заполнен; все расхождения с ТЗ задокументированы в NOTES.

**Подводные камни.** Тесты TCP-порта должны использовать нестандартные порты и чиститься за собой; тесты не должны требовать реального API-ключа.
