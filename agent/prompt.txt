# Проект PIBOX — безопасный запуск Pi Coding Agent в Docker

## 1. Контекст и цель проекта

**Pi Coding Agent** ([pi.dev](https://pi.dev/)) — это минималистичный терминальный AI-агент для разработки с архитектурой "anti-framework". Он использует всего 4 базовых инструмента (`read`, `write`, `edit`, `bash`), хранит сессии в виде деревьев `.jsonl` внутри `~/.pi/agent/sessions/` и позволяет подключать расширения, скиллы и пользовательские промпты.

**Задача:** обеспечить безопасный запуск `pi_coding_agent` локально, в изолированном Docker-контейнере, с сохранением состояния агента между сессиями и возможностью гибко управлять рабочими окружениями.

---

## 2. Структура проекта на хосте (исходники `pibox`)

В корне репозитория находятся:

| Файл / Директория | Назначение |
|---|---|
| `run.sh` (или аналог) | Скрипт запуска контейнера |
| `entrypoint.sh` | Скрипт-инициализатор внутри контейнера |
| `env-template/` | Шаблон базового содержимого `/home/pi` для новых окружений. Хранит конфиги Pi (расширения, инструменты, скиллы) и дополнительные приложения, используемые расширениями |
| `Dockerfile` | Сборка образа |
| `README.md` | Документация |
| `install.sh` | Скрипт установки проекта на хост |

## 3. Скрипт установки (`install.sh`)

При запуске установщик выполняет следующие шаги:

1. Создаёт директорию по указанному пути (например, из переменной окружения `PIBOX_DIR = ~/pibox`).
2. Копирует скрипт `PIBOX_DIR/bin/pibox` — **единственную точку входа** (поддерживает подкоманды).
3. При необходимости прописывает `PIBOX_DIR/bin` в `PATH`.
4. Копирует `env-template` из директории-исходника в `PIBOX_DIR`.
5. Внутри `PIBOX_DIR` создаётся поддиректория `./env/default`, куда копируется содержимое `env-template`.
6. В `PIBOX_DIR/env/` размещается файл `models.json`, который перед первым запуском контейнера копируется в соответствующее окружение (например, `./env/default/.pi/agent/models.json`), если его там ещё нет.

---

## 4. Управление окружениями (`env`)

### 4.1 Принцип работы
- По умолчанию при запуске монтируется `./env/default` в `/home/pi` внутри контейнера.
- Если при запуске указано другое окружение (например, `php8`), монтируется `./env/php8`.
- Если запрошенное окружение отсутствует — оно автоматически создаётся из `env-template`.
- Каждое окружение хранит: конфиги Pi, ключи, пользовательские расширения, скиллы, а также локально установленные тулчейны, библиотеки и приложения, необходимые агенту.

### 4.2 Модели и API (`models.json`)
- Хранится в `PIBOX_DIR/env/<имя>/.pi/agent/models.json`.
- Копируется из `PIBOX_DIR/env/models.json` при первом запуске окружения.
- Для доступа к локальному Model API используется адрес `http://host.docker.internal:8080`.

## 5. Docker-образ

### 5.1 Базовый образ
Образ собирается на основе **последней стабильной Ubuntu**.

### 5.2 Многостадийная сборка и пакеты
Чтобы минимизировать размер образа, применяется multi-stage подход. Пакеты разделены на две группы:

#### ✅ Базовый набор (входит в финальный образ)
Это пакеты, необходимые для работы самого Pi-агента и базовых операций:

**Системные:**
`ca-certificates`, `locales`, `tzdata`, `lsb-release`, `gosu`, `tini`, `cat`, `less`, `grep`, `sed`, `find`, `xargs`, `gawk`, `diffutils`, `file`, `xxd`, `procps`, `psmisc`, `tmux`

**Сеть и безопасность:**
`curl`, `wget`, `openssl`, `iproute2`, `iputils-ping`, `openssh-client`, `dnsutils`, `lsof`

**Работа с файлами и архивами:**
`git`, `tar`, `gzip`, `unzip`, `rsync`, `zip`, `bzip2`, `xz-utils`, `zstd`, `lz4`

**Python и Node.js:**
`python3`, `python3-pip`, `python3-venv`, `nodejs`, `npm`

**Инструменты разработчика и утилиты:**
`jq`, `ripgrep`, `yq`, `vim`, `htop`, `ncdu`, `hexedit`

**Для установки языков локально:**
`mise`

**Самое главное ради чего делается сборка - установка pi-coding-agent (https://pi.dev/) :**
`npm install -g --ignore-scripts @earendil-works/pi-coding-agent`

Важно: надо убедиться что все установки в образе выполняются глобально (не в home) потому что home будет монтироваться 
снаружи.

#### 🔧 Расширенный набор (устанавливается агентом локально)
Тяжёлые тулчейны и отладочные утилиты **не включаются в образ**. Агент устанавливает их локально в `~/.local` через версионера  `mise` при первом запуске в новом окружении. Установленное сохраняется в соответствующем `env/<name>` и используется повторно.

К тяжёлым относятся:
`cmake`, `golang`, `rustc`, `cargo`, `gdb`, `valgrind`, `strace`, `sysstat`, `iotop`, `tcpdump`

Это позволяет:
- держать финальный образ компактным;
- гибко подбирать стек под конкретную задачу (php8, rust, python и т.д.);
- сохранять установленные тулчейны в `env-template` для переиспользования.

### 5.3 Сохранение эталонного home (`/opt/skel`)
Поскольку при запуске `/home/pi` полностью подменяется bind-mount'ом, всё содержимое home'а, созданное при сборке образа, становится невидимым. Чтобы dotfiles (`.bashrc`, `.profile`, `.npmrc` и т.п.), созданные установщиками пакетов, не терялись:

- В `Dockerfile` эталонный home сохраняется в `/opt/skel`.
- В `entrypoint.sh` выполняется **мердж** недостающих файлов:
  ```bash
  cp -rn /opt/skel/. /home/pi/
  ```
  Копируются только те файлы, которых ещё нет в примонтированном окружении, не затирая пользовательские конфиги.

## 6. Запуск контейнера

### 6.1 Пользователь и монтирование workspace
- Агент `pi` запускается **от внутреннего пользователя `pi`** контейнера.
- Текущая директория хоста монтируется в `/home/pi/workspace` (с правами чтения/записи).
- Агент стартует именно на этой директории.

Пример использования:
```bash
cd ~/project1
pibox
# project1 примонтируется как /home/pi/workspace, и Pi начнёт работу с ней
```

### 6.2 Динамическая подстройка UID/GID
На хосте пользователь может иметь любой UID — мы не закладываемся на 1000. Поэтому **в `entrypoint.sh`** происходит динамическая подстройка UID/GID пользователя `pi` под UID/GID пользователя хоста. Это гарантирует, что файлы, создаваемые агентом в `workspace`, будут принадлежать хост-пользователю, а не `root`.

### 6.3 Entrypoint: последовательность действий
```bash
1. Подстроить UID/GID пользователя pi под хост
2. При первом запуске выполнить копирование из /opt/skel в /home/pi. Далее оставить некий признак что копирование состоялось и не делать его при последующих запусках
3. Передать управление через gosu pi:pi tini -- pi "$@"
```

### 6.4 Сетевые возможности и capabilities
По умолчанию контейнер имеет доступ:
- к **интернету** (для поиска документации);
- к **локальной сети** (для доступа к Model API).

Специальные capabilities добавляются в скрипте запуска:
- `--cap-add=SYS_PTRACE` — для работы `strace`, `gdb`;
- `--cap-add=NET_RAW` — для работы `tcpdump` и сетевых утилит.

Также в скрипте запуска добавляется маппинг:
```
--add-host host.docker.internal:host-gateway
```
Это позволяет контейнеру обращаться к сервисам на хост-машине (например, локальному API) по адресу `http://host.docker.internal:8080`.

### 6.5 Ограничения ресурсов
Контейнер запускается с разумными ограничениями CPU и памяти, чтобы агент не мог исчерпать ресурсы хоста.

## 7. Безопасность и проверки

### 7.1 Проверка workspace
Запускающий скрипт **тщательно проверяет**, чтобы рабочая директория не являлась ни дочерней, ни родительской по отношению к `PIBOX_DIR` (проверка выполняется через `realpath`, чтобы корректно обрабатывать symlink'и). В противном случае скрипт завершается ошибкой — это защищает от случайного редактирования или удаления конфигов самого `pibox`.

### 7.2 Git safe.directory
Имеется опция включения `git safe.directory` для `workspace`, чтобы git не ругался на смену владельца файлов после bind-mount'а.

### 7.3 Проброска портов
Контейнер поддерживает проброску пользовательских портов (например, для запуска локального dev-сервера внутри контейнера).

### 7.4 Docker Compose
**Не используется.** Всё управляется через shell-скрипты и прямые `docker run` команды.

---

## 8. Резюме архитектурных решений

| Аспект | Решение |
|---|---|
| Состояние агента | Bind-mount `./env/<name>` → `/home/pi`, шаблон `env-template` |
| Модели окружений | `default`, `php8` и произвольные, создаются автоматически из шаблона |
| Размер образа | Multi-stage сборка, тяжёлые тулчейны устанавливаются локально в `~/.local` |
| Dotfiles | Эталон сохраняется в `/opt/skel`, мерджится в `entrypoint.sh` |
| UID/GID | Динамическая подстройка в `entrypoint.sh` |
| Безопасность workspace | Проверка через `realpath`, запрет вложенности |
| Сетевой доступ | `host.docker.internal` + capabilities `SYS_PTRACE`, `NET_RAW` |
| API-ключи | Передача через переменные окружения, а не только через `models.json` |
