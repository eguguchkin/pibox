# План реализации проекта PIBOX

## Общая идея проекта
**PIBOX** – это инструмент для безопасного локального запуска AI-агента **Pi Coding Agent** в изолированном Docker-контейнере. Проект предоставляет:
- единую точку входа – команду `pibox`;
- управление изолированными окружениями (среды для разных стеков);
- автоматическую установку и настройку;
- безопасный доступ к рабочей директории и сетевым ресурсам;
- сохранение состояния агента между сессиями.

## Задачи реализации

### Задача 1. Создание файловой структуры проекта и шаблонов
**Суть задачи:** подготовить дерево каталогов и начальные файлы, которые будут использоваться всеми остальными компонентами.

**Детали для исполнителя:**
1. Создать корневую директорию проекта (например, `pibox/`). Внутри неё разместить:
   - `bin/` – для исполняемых скриптов (в будущем туда попадёт `pibox`);
   - `env-template/` – шаблон базового окружения;
   - `Dockerfile`, `entrypoint.sh`, `run.sh` (или `pibox`), `install.sh`, `README.md`.
2. В `env-template/` создать структуру, соответствующую домашней директории пользователя `pi` внутри контейнера:
   - `.pi/agent/` – здесь будут храниться сессии, конфиги, модели и т.д.;
   - `.local/` – для локально установленных тулчейнов (через `mise`);
   - `.bashrc`, `.profile` – базовые файлы окружения;
   - `.npmrc`, `.gitconfig` – по необходимости.
3. Создать файл `env/models.json` в корне проекта (он будет копироваться в каждое окружение при первом запуске). Этот файл должен содержать пример конфигурации моделей (можно взять с сайта pi.dev или оставить заготовку с указанием `http://host.docker.internal:8080`).
4. Убедиться, что все скрипты имеют права на исполнение (chmod +x) после установки.

### Задача 2. Разработка скрипта установки `install.sh`
**Суть задачи:** создать инсталлятор, который разворачивает проект на хосте, копирует бинарный файл `pibox` в `PATH` и подготавливает стандартное окружение.

**Детали для исполнителя:**
1. Скрипт должен принимать опциональный параметр – путь установки (по умолчанию `~/pibox`). Например:
   ```bash
   PIBOX_DIR="${1:-$HOME/pibox}"
   ```
2. Проверить, существует ли `PIBOX_DIR`; если нет – создать (`mkdir -p "$PIBOX_DIR"`).
3. Скопировать все файлы из исходной директории (где лежит `install.sh`) в `PIBOX_DIR`, исключая сам `install.sh` (или копировать всё, кроме него). Особенно важно скопировать `bin/pibox`, `env-template`, `Dockerfile`, `entrypoint.sh`, `run.sh`, `README.md`.
4. Создать внутри `PIBOX_DIR` каталог `env/` и скопировать в него содержимое `env-template` как первое окружение `default`:
   ```bash
   mkdir -p "$PIBOX_DIR/env/default"
   cp -r "$PIBOX_DIR/env-template/." "$PIBOX_DIR/env/default/"
   ```
5. Скопировать `models.json` из корня проекта в `PIBOX_DIR/env/models.json` (если его ещё нет). Этот файл будет использоваться как эталон для новых окружений.
6. Добавить `PIBOX_DIR/bin` в `PATH` пользователя, если это необходимо. Можно предложить добавить строку в `~/.bashrc`:
   ```bash
   echo 'export PATH="$HOME/pibox/bin:$PATH"' >> ~/.bashrc
   ```
   Но лучше спросить у пользователя или вывести инструкцию.
7. Проверить, что `docker` установлен и доступен; если нет – вывести предупреждение.
8. В конце вывести сообщение об успешной установке и напомнить, как использовать команду `pibox`.

### Задача 3. Сборка Docker-образа через `Dockerfile` (multi-stage)
**Суть задачи:** создать `Dockerfile`, который собирает минимальный образ с Ubuntu, устанавливает базовые пакеты, сохраняет эталонный home в `/opt/skel` и подготавливает окружение для запуска агента.

**Детали для исполнителя:**
1. Использовать многостадийную сборку, чтобы уменьшить размер финального образа.

Однако в описании сказано, что тяжёлые тулчейны не входят в образ, а устанавливаются агентом локально. Значит, в `Dockerfile` мы устанавливаем только базовый набор пакетов (перечислены в разделе 5.2).
3. Базовый образ – `ubuntu:latest` или `ubuntu:22.04` (стабильная LTS).

9. Указать рабочую директорию `/home/pi/workspace` (но она будет переопределена при монтировании).
10. Указать `ENTRYPOINT ["/entrypoint.sh"]` и `CMD ["pi"]` (или `["/usr/bin/pi"]`, но сам `pi` агент будет установлен позже через `mise` или скрипт? Тогда в `Dockerfile` нужно установить его глобально или через `mise`. Но логичнее установить в окружении через `mise` или npm, чтобы он был доступен. В `env-template` можно прописать установку. Это может быть задачей для `entrypoint.sh`. Поэтому в `Dockerfile` мы не устанавливаем `pi`, а только создаём среду.

12. Собрать образ с тегом, например, `pibox:latest`.

### Задача 4. Разработка скрипта `entrypoint.sh`
**Суть задачи:** создать скрипт, который выполняется при запуске контейнера, подстраивает UID/GID, мерджит эталонные dotfiles из `/opt/skel` и запускает агент от имени пользователя `pi`.

**Детали для исполнителя:**
1. Скрипт должен быть написан на bash и начинаться с `#!/bin/bash`.
2. Первым делом определить UID и GID пользователя хоста. Так как при запуске контейнера мы монтируем том с workspace, мы можем получить владельца файлов в `/home/pi/workspace` и использовать его. Либо мы можем передать UID/GID через переменные окружения (например, `HOST_UID`, `HOST_GID`). В описании сказано "динамическая подстройка UID/GID пользователя pi под UID/GID пользователя хоста". Проще всего в скрипте запуска (на хосте) определить `id -u` и `id -g` и передать их как переменные окружения в контейнер. Тогда `entrypoint.sh` может использовать их.
   Вариант: в `entrypoint.sh`:
   ```bash
   HOST_UID=${HOST_UID:-1000}
   HOST_GID=${HOST_GID:-1000}
   ```
   Далее проверить, существует ли группа с GID `$HOST_GID`; если нет – создать. Аналогично для пользователя.
   ```bash
   if ! getent group $HOST_GID >/dev/null; then
       groupadd -g $HOST_GID pi_group
   fi
   if ! getent passwd $HOST_UID >/dev/null; then
       useradd -m -u $HOST_UID -g $HOST_GID -s /bin/bash pi
   else
       # если пользователь с таким UID уже существует, возможно, это не pi; нужно переименовать? 
       # Лучше использовать существующего пользователя, но нам нужен именно пользователь pi с нужным UID.
       # Можно изменить UID существующего pi.
   fi
   ```
   Более простой подход: всегда использовать пользователя `pi` и менять его UID/GID. В `entrypoint.sh`:
   ```bash
   # Получаем UID/GID из переменных окружения (устанавливаются при запуске)
   PUID=${PUID:-1000}
   PGID=${PGID:-1000}
   # Изменяем UID/GID пользователя pi
   usermod -u $PUID pi 2>/dev/null && groupmod -g $PGID pi 2>/dev/null
   ```
   Это может привести к конфликтам, если такие UID/GID уже заняты другими пользователями, но в контейнере обычно мало пользователей. Можно сделать проверку и занять свободный, но проще использовать `gosu` для выполнения команд от имени владельца workspace. Альтернатива: вообще не менять пользователя, а использовать `gosu` для запуска от имени владельца файлов workspace, определяя владельца динамически. В описании сказано "динамическая подстройка UID/GID пользователя pi под UID/GID пользователя хоста". Так что будем менять UID/GID пользователя pi.
   Рекомендую:
   ```bash
   # Получаем UID и GID хоста из переменных, переданных при запуске
   HOST_UID=${HOST_UID:-1000}
   HOST_GID=${HOST_GID:-1000}
   # Проверяем, не занят ли этот UID другим пользователем
   if [ "$(id -u pi)" != "$HOST_UID" ]; then
       usermod -u $HOST_UID pi
   fi
   if [ "$(id -g pi)" != "$HOST_GID" ]; then
       groupmod -g $HOST_GID pi
   fi
   # Также нужно убедиться, что домашняя директория принадлежит pi
   chown -R pi:pi /home/pi
   ```
3. Мердж dotfiles из `/opt/skel` в `/home/pi`:
   ```bash
   cp -rn /opt/skel/. /home/pi/
   ```
   Это копирует только те файлы, которых нет, не перезаписывая существующие.
4. Проверить, установлен ли `pi_coding_agent`. Если нет – установить его через npm (или через `mise`). Например:
   ```bash
   if ! command -v pi &> /dev/null; then
       npm install -g @pi-dev/cli
   fi
   ```
   Но это может быть нежелательно, если мы хотим, чтобы установка происходила в окружении. Альтернативно, можно положить установку в скрипт, который выполняется при первом запуске окружения. Можно создать файл-маркер `~/.pi/installed` и проверять его. В любом случае, для упрощения можно установить `pi` глобально в `Dockerfile`, тогда он будет общим для всех окружений. Однако по описанию, агент устанавливается в окружении? В разделе 4.1 сказано, что окружение хранит конфиги Pi, ключи, расширения, скиллы, а также локально установленные тулчейны. Сам `pi` вероятно является npm-пакетом и может быть установлен глобально, но конфиги лежат в `~/.pi`. Так что можно установить `pi` в образе глобально, тогда все окружения будут его использовать. Это проще. Поэтому в `Dockerfile` добавим `RUN npm install -g @pi-dev/cli` (или через `mise`). Но тогда он будет общим, что не противоречит описанию. Решим: установим `pi` в образе через npm, чтобы не ждать при каждом запуске. Тогда `entrypoint.sh` не должен заниматься установкой.
5. После подстройки и мерджа, передать управление через `gosu`:
   ```bash
   exec gosu pi:pi tini -- pi "$@"
   ```
   Здесь `$@` – аргументы командной строки, переданные в контейнер.
6. Важно: скрипт должен быть исполняемым и располагаться в корне контейнера (`/entrypoint.sh`).

### Задача 5. Разработка основного скрипта управления `pibox` (ранее `run.sh`)
**Суть задачи:** создать скрипт, который является единственной точкой входа на хосте. Он обрабатывает подкоманды (запуск, создание окружения, список окружений, удаление и т.д.), проверяет безопасность рабочей директории, формирует и выполняет команду `docker run` с нужными параметрами.

**Детали для исполнителя:**
1. Скрипт должен располагаться в `PIBOX_DIR/bin/pibox` и быть исполняемым. Он должен принимать подкоманды:
   - `pibox` (без аргументов) – запуск агента в текущей директории с окружением `default` (или указанным через переменную окружения `PIBOX_ENV`).
   - `pibox env create <name>` – создать новое окружение.
   - `pibox env list` – показать список окружений.
   - `pibox env remove <name>` – удалить окружение (с подтверждением).
   - `pibox build` – пересобрать Docker-образ.
   - `pibox --help` – справка.
2. Переменные окружения:
   - `PIBOX_DIR` – корневая директория проекта (по умолчанию `~/pibox`).
   - `PIBOX_ENV` – имя окружения (по умолчанию `default`).
   - `PIBOX_IMAGE` – имя Docker-образа (по умолчанию `pibox:latest`).
3. Определить местоположение `PIBOX_DIR`. Если не задано, попытаться определить по расположению скрипта (например, `$(dirname $(realpath $0))/..`). Но установщик копирует скрипт в `bin/`, поэтому корень – на уровень выше.
4. Проверка рабочей директории (workspace):
   - Получить абсолютный путь текущей директории (через `realpath .`).
   - Получить абсолютный путь `PIBOX_DIR` (через `realpath`).
   - Проверить, не является ли текущая директория дочерней или родительской по отношению к `PIBOX_DIR`. Для этого сравнить строки: если `workspace` начинается с `PIBOX_DIR` или наоборот, то выдать ошибку и завершиться. Это защищает от случайного удаления/изменения конфигов.
5. Обработка окружений:
   - При запуске (без подкоманд) проверить, существует ли `PIBOX_DIR/env/$PIBOX_ENV`. Если нет – создать его из шаблона (`env-template`).
   - Также проверить наличие `$PIBOX_DIR/env/$PIBOX_ENV/.pi/agent/models.json`; если отсутствует – скопировать из `$PIBOX_DIR/env/models.json`.
6. Формирование команды `docker run`:
   - Параметры монтирования:
     - `-v "$PIBOX_DIR/env/$PIBOX_ENV:/home/pi"`
     - `-v "$(pwd):/home/pi/workspace"`
   - Переменные окружения для `entrypoint.sh`: `HOST_UID=$(id -u)`, `HOST_GID=$(id -g)`.
   - Дополнительные параметры:
     - `--rm` (удалять контейнер после завершения)
     - `--cap-add=SYS_PTRACE --cap-add=NET_RAW`
     - `--add-host host.docker.internal:host-gateway`
     - Ограничения ресурсов: `--cpus=2 --memory=4g` (можно сделать настраиваемыми через переменные).
     - Если нужен проброс портов, добавить `-p` параметры (можно передать через переменную `PIBOX_PORTS`).
   - Передать аргументы командной строки в контейнер (после `--`).
   - Запускать от текущего пользователя? Нет, внутри контейнера работает `pi`, но `docker run` выполняется от пользователя хоста.
   - Использовать `--user`? Нет, мы подстраиваем UID внутри.
   - Использовать `-it` если терминал интерактивный (проверить `-t`).
7. Обработка сигналов: можно использовать `trap` для корректного завершения.
8. После выполнения контейнера, скрипт завершается с тем же кодом возврата, что и контейнер.

### Задача 6. Создание шаблона окружения `env-template` и эталонного `models.json`
**Суть задачи:** подготовить содержимое `env-template`, которое будет служить базой для всех новых окружений, и файл `models.json` с конфигурацией моделей.

**Детали для исполнителя:**
1. В `env-template/` создать структуру, которая будет скопирована в новое окружение:
   - `.bashrc` – базовый, с настройками `mise`, путями и т.д. (можно включить инициализацию `mise`).
   - `.profile` – аналогично.
   - `.pi/` – директория для конфигов агента.
   - `.pi/agent/` – будет содержать `models.json` (который копируется отдельно) и другие файлы (сессии будут создаваться автоматически).
   - `.local/` – для установленных тулчейнов.
   - Также можно добавить `.gitconfig` с `safe.directory` для workspace.
2. В корне `PIBOX_DIR/env/` разместить `models.json` – эталонную конфигурацию для моделей. Примерное содержание:
   ```json
   {
     "models": [
       {
         "name": "local",
         "provider": "openai",
         "baseUrl": "http://host.docker.internal:8080/v1",
         "apiKey": "not-needed"
       }
     ]
   }
   ```
   Это позволит использовать локальный Model API.
3. В `env-template/.pi/agent/` можно разместить пустой `models.json` (или не размещать, чтобы копировался при первом запуске).
4. Добавить файл `.mise.toml` или настроить `mise` через `.bashrc`, чтобы тулчейны устанавливались в `~/.local/share/mise`.

### Задача 7. Интеграция проверок безопасности и ограничений
**Суть задачи:** реализовать в скрипте `pibox` все проверки безопасности, описанные в разделе 7, и добавить механизмы ограничения ресурсов.

**Детали для исполнителя:**
1. Проверка workspace (в задаче 5 уже упоминалась) – реализовать через `realpath` и сравнение строк.
2. Включение `git safe.directory` для workspace. Можно добавить в `entrypoint.sh` или в `env-template/.gitconfig`:
   ```
   [safe]
       directory = /home/pi/workspace
   ```
   Это можно сделать динамически, передав путь в переменную, или просто прописать в .gitconfig внутри окружения.
3. Проброс портов: в `pibox` добавить возможность указания портов через переменную `PIBOX_PORTS` (формат `"8080:8080 3000:3000"`) и передавать их в `docker run` как несколько `-p`.
4. Ограничения ресурсов: задать значения по умолчанию (например, `--cpus=2 --memory=4g`) и сделать их настраиваемыми через переменные `PIBOX_CPUS`, `PIBOX_MEMORY`.
